# 文件变动后 Files 列表不刷新

## 发生了什么

在 macOS 的独立 Con Beta build 127 实例中，Files 面板打开后，新建文件、重命名文件以及将文件移出目录，磁盘已经变化但列表仍显示原来的条目。折叠根目录后重新展开，普通文件列表才更新。

## 根因

文件树只在根目录切换或目录展开时读取文件系统。同一个根目录再次传给 `set_root` 会直接返回，没有文件系统监听来触发结构刷新。

评审还发现初版监听实现的两项平台差异：Linux 的 inotify 在目录被删除/移动后可能撤销订阅，缓存的路径集合无法代表订阅仍有效；notify 7 在 Windows 将普通内容写入报告为 `Modify(Any)`，不能把它一律当作目录结构变化。

## 修复

- 使用仓库已有的 `notify` 依赖监听目录结构事件；仅监听展开的目录及根目录的父目录，不递归监听折叠或隐藏的子树。
- 合并短时间内的事件，将订阅更新和目录读取放到后台，仅在可见列表变化时通知 UI。
- 使用展开路径集合重建可见树，保留仍存在的目录展开状态及当前打开文件路径。
- 通过请求代次阻止旧扫描覆盖新根目录、重新打开已折叠的分支或撤销较新的监听订阅；切换根目录或销毁实体时释放旧监听。
- 删除/移动事件使受影响目录及其子目录的订阅失效，刷新时重新注册。失效标记独立于合并事件的唤醒队列保存，同时保留原始与 canonical 路径；普通文件删除不会重建父目录订阅。注册/取消监听时不持有回调使用的锁，避免后端等待回调退出时死锁。
- Windows 的普通 `Modify(Any)` 通知不触发整树扫描；新增、删除、改名、rescan 和错误恢复仍触发刷新。
- 保留原有点文件与点目录过滤规则。本次仅处理 #206 的刷新部分。

## 验证

- 修复前的独立 Con Beta build 127 界面对照已确认：新增、改名和移出不会自动更新，折叠再展开才恢复。
- `cargo test --offline --locked -p con --bin con file_tree_view::tests::`：重新编译后 17 项全部通过，覆盖事件筛选、增删改、展开与选中状态保留、折叠后的旧扫描、根目录切换、无变化时复用缓存、原生监听及资源释放。新增回归覆盖 Windows 的实际 `Modify(Any)` 事件类型、目录删除/移动后失效路径及其子树、取消旧订阅并替换同路径目录后能继续收到文件创建事件。原生监听测试需要允许系统监听与编译缓存写入，受限沙箱下的超时不等于修复版测试通过。
- `cargo build --offline --locked -p con --bin con`、修改文件的 `rustfmt --check`、`git diff --check` 均通过。
- 在独立测试应用中替换为修复版，Files 保持打开，展开 `src` 并打开 `keep.rs`。通过外部文件系统操作创建 `new.txt` 和 `new-folder`，将 `old.txt` 改为 `renamed.txt`，删除 `remove.txt`，并在 `src` 新增 `added.rs`。没有点击刷新或折叠目录，列表自动反映全部变化；`src` 仍展开，`keep.rs` 仍选中且编辑器内容保持不变。
- 界面确认磁盘上存在的 `.git`、`.venv`、`.gitignore` 继续隐藏。
- 评审修复后的独立应用中展开 `new-folder` 与 `src`，在 0.3 ms 内删除重建 `new-folder`、将 `src` 移出根目录后放回同一路径。等待本轮事件处理后再分别新增 `after-recreate.txt` 和 `after-move.rs`，无需操作文件树，两个新增条目自动显示，目录保持展开。
- 本地编译、原生监听及实际界面验证平台为 macOS；Windows/Linux 尚未实机验证。

## 经验

文件树的数据缓存必须由文件系统变化驱动失效。异步刷新除了保护 UI 的请求顺序，还需要保护监听订阅的更新顺序。

文件系统通知的平台语义不同；不能用“路径仍存在”判断监听订阅仍存活，也不能用单个平台的事件种类推断其他后端的内容通知。可丢弃/合并唤醒信号，但恢复订阅所需的信息必须独立保留。

GPUI 测试的实体释放是延迟执行的。测试销毁视图后的资源释放时，`drop(view)` 后需要先通过 `cx.update(|_| {})` 完成释放周期，再运行调度器并检查监听器引用；仅 `run_until_parked()` 不会处理 App 的释放 effects。
